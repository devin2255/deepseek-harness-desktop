# Agent Note：配置驱动的运行时包闭包

Status: implemented

[English](2026-09-14-configured-runtime-package-closure.md) | 中文

## 问题

Python SDK 运行时 manifest 过去只验证 npm 静态依赖和必需 peer。Cordis 配置文件会在运行时按包名加载插件，因此即使静态依赖图已闭合，部署根目录仍可能缺少配置引用的插件。发布流水线要先花时间构建单文件可执行程序，直到首次启动时才暴露缺包问题。

## 决策

运行时闭包门禁会解析 Python 运行时发布冒烟测试使用的所有已检入 Cordis 配置：内置默认配置、完整 JSON-RPC agent 配置和最小 JSON-RPC agent 配置。除了原有的必需 peer 闭包规则，每个被引用的工作区插件还必须是 `python/sdk-runtime/package.json` 的直接工作区依赖。

自定义 manifest 检查可以通过重复的 `--config` 参数显式提供配置路径。未提供配置参数的自定义 manifest 仍只执行依赖闭包验证。

## 验证

发布冒烟配置引用了运行时 manifest 中不存在的工作区插件时，门禁会在打包前失败。已检入运行时 manifest 包含两个 JSON-RPC agent 配置都会挂载的 `@deepseek-ai/dsh-task-session`。原生发布工作流仍会启动生成的可执行程序，并运行完整、最小、快照、直接二进制和零配置场景。

## 考虑过的替代方案

**只依赖可执行程序冒烟测试。** 这种方式能发现缺陷，但必须等昂贵的构建完成，而且不能直接指出 manifest 与配置不一致。

**从 npm 传递依赖推断配置插件。** Cordis 从部署根目录解析裸包名；偶然存在的传递依赖不是受控或稳定的解析路径。

**把所有工作区包复制进可执行程序。** 这会扩大产物和能力范围，却没有对应的运行时用途。

## 后果

- 配置与打包内容发生漂移时，会在原生构建前由仓库门禁失败。
- 发布冒烟配置新增工作区插件时，也必须显式新增一项运行时 manifest 依赖。
- 运行时包集合继续只包含有意声明的部署内容。
