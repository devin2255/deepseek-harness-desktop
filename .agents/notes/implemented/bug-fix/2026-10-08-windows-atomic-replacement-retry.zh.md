# Agent Note: 有界的 Windows 原子替换重试

Status: implemented

[English](2026-10-08-windows-atomic-replacement-retry.md) | 中文

## 问题

Windows 可能在其他句柄临时占用现有设置文档时，以 `EPERM` 拒绝替换。真实组合的浏览器设置操作会收到 `settings-rejected`，持久化偏好保持不变。同一原子写入原语也负责发布凭据，因此只重试浏览器操作会让其他消费方继续受影响。

## 决策

`dsh-atomic-write` 对 Windows 的 `EPERM`、`EACCES` 和 `EBUSY` rename 失败进行重试，始终使用同一份已准备好的临时文件和目标路径。基于单调时钟的一秒重试预算采用从 10 ms 增长到 100 ms 的指数退避，且每次延迟不超过剩余预算。rename 成功即为发布点。预算耗尽时重新抛出最后一次文件系统错误；无关错误与其他平台立即失败。

发布过程绝不删除目标文件、重写已准备好的内容或退回非原子复制。失败清理只删除本次操作的临时文件。这些重试限制是固定的文件系统协议边界，低于写入锁的两秒获取期限，不是插件部署设置。它们不会取消进行中的文件系统调用，也不会改变[设置写入锁与读-修改-写规则](../architecture/2026-07-30-settings-write-path-integrity.md)。

## 考虑过的替代方案

**使用 `graceful-fs`。** 它的 [Windows rename 包装器](https://github.com/isaacs/node-graceful-fs/blob/main/polyfills.js) 只在随后对目标执行 stat 返回 `ENOENT` 时重试，因此不会重试替换现有文档。它允许的 60 秒重试时间也超过了此存储的写入锁获取预算。

**删除目标文件或直接覆盖内容。** 两者都会失去读取方只能看到旧内容或完整新内容的保证；发布失败可能丢失原有设置或暴露不完整内容。

**重试整个设置修改。** 发布已准备好的替换文件不需要重新渲染文档，而且仅浏览器侧的重试无法保护凭据或其他设置调用方。发布重试保留在现有写入锁内部。

**在所有平台上重试所有错误。** 路径缺失、I/O 失败和非 Windows 权限失败不能证明存在临时共享占用。延迟这些错误会掩盖可处理的故障，却没有支持证据。

## 影响

Windows 临时共享占用失败不再需要用户重复操作。持续存在的权限失败可能额外等待一秒后才被拒绝。原子性、独占创建临时文件、调用方指定的模式位、锁所有权和设置的最后有效状态发布机制保持不变。本修复不会为此工具增加 fsync 持久性或 Windows DACL 保留；[DACL 替换决策](2026-07-19-windows-atomic-write-dacl-preservation.md) 负责独立的 `dsh-fs-local` 实现。

[Host 持久化偏好决策](2026-08-06-host-backed-web-preferences.md) 仍负责浏览器同步，[请求级配置决策](../architecture/2026-07-29-request-level-llm-config-credentials.md) 仍负责凭据引用和共享工具的消费方。这些独立决策均未被取代。

## 验证

与宿主平台无关的故障注入覆盖三个可重试错误码、完全相同的 rename 参数、仅写入一次内容、期限耗尽、保留最后错误、无关错误及 POSIX 立即失败。设置与凭据提供方测试保留跨实例串行化、失败清理和文件监听覆盖。无需密钥的真实组合浏览器设置场景注入两次原生 Windows rename 失败，验证偏好持久化，并保留现有 UI 快照、重新加载和不同端口检查。它不调用模型 API，也不改变任何预期输出。
