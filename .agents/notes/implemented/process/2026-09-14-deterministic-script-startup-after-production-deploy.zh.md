# Agent Note：生产部署后的确定性脚本启动

状态：已实施

[English](2026-09-14-deterministic-script-startup-after-production-deploy.md) | 中文

## 问题

桌面端打包流程通过 `pnpm deploy --prod --legacy` 暂存仅包含生产依赖的运行时。pnpm 11 会把该依赖模式记录在工作区状态中。在默认的 `verifyDepsBeforeRun: install` 设置下，后续的 `pnpm run` 或 `pnpm exec` 可能在仓库根目录隐式执行生产依赖安装。该改写会在安装包验证或端到端测试启动前删除开发依赖，随后根目录的 postinstall 会因为缺少仅用于开发的工具而失败。

这种行为使命令启动结果取决于此前执行过的部署操作，也会让只读验证命令修改开发者或 CI 共用的依赖树。

## 决策

工作区设置 `verifyDepsBeforeRun: false`。仓库脚本不得触发隐式依赖安装或改写；依赖安装必须由开发者或 CI 准备步骤显式执行。CI 在构建前仍执行不可变安装。

桌面包验证和安装器端到端工作流在打包后直接调用仓库内固定的 Node 入口。即使未来 pnpm 设置发生变化，发布验证也不依赖 pnpm 记录的部署模式。

## 验证

桌面安装器工作流测试会断言工作区设置以及打包后使用的直接 Node 命令。依次运行 `pnpm run desktop:stage` 和 `pnpm run desktop:validate-package`，证明生产暂存不会再在验证前删除开发依赖。Windows 托管安装器工作流随后会在隔离的用户目录中构建、验证、安装、启动并卸载发布产物。

## 考虑过的替代方案

**每次生产部署后恢复开发依赖。** 这会增加第二次工作区改写，延长发布耗时，并可能掩盖对仓库状态的未声明依赖。

**仅在 CI 中使用直接 Node 命令。** 这能保护工作流，但文档中的开发者命令仍可能遭受相同的隐式改写。

**抑制 postinstall 失败。** 这会允许依赖删除继续发生，只隐藏它最先出现的症状。

## 后果

- 脚本启动具有确定性，不会修改已安装依赖。
- 缺失或陈旧的依赖会在需要它的命令处失败；操作者必须显式运行 `pnpm install`。
- 生产暂存后可以在同一检出中继续运行验证或测试，无需恢复开发依赖。
- 即使 pnpm 对部署状态的解释发生变化，发布工作流命令仍可使用。
